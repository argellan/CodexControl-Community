This optional integration adds a rebuildable DuckDB projection of checksum-verified usage archive segments. V1/V2 records supply the usage reports. Receiver-validated V3 GitHub metadata can share the archive: its exact bytes and provenance are retained, with no token interpretation or inclusion in usage totals. Older receivers still refuse V3, and unsupported future families fail closed. The immutable archive is authoritative. The analytical database must stay on the engine host's local disk; temporary disk spill is disabled. Projection never acknowledges Pi custody, edits receiver catalog rows, changes archive retention, or deletes captured history. The existing optional Timescale template is not activated by this integration.

## Integration contract

The Python entry point is `scripts/archive-analytics.py`. A separate private configuration identifies `receiverConfig` (absolute path to the existing receiver configuration), `databaseDirectory` (absolute local path), `memoryLimitMb` (64–1024, default 256), `threads` (1–4, default 2), and `queryTimeoutSeconds` (1–30, default 15), with `version: 1`. The engine dependency is pinned separately in `scripts/analytics-requirements.txt`; ordinary hub/collector execution remains dependency-free.

`--sync --limit N` imports at most N verified segments (1–32) per invocation. Full canonical record lines, record/item identities, original source row data, content addresses and segment membership are retained in the projection. Item replay is idempotent, conflicting item bytes are refused, and the projection segment ledger commits in the same transaction as its rows. Restart/retry can therefore recover after interrupted projection independently of the archive receiver. `--status` describes projection lag. `--query` accepts one bounded JSON document on stdin and returns one bounded JSON report on stdout. It never accepts caller SQL. Query errors are generic structured codes without raw source values, paths or subprocess diagnostics. A missing projection is unavailable, not empty history.

Query request (all unknown or duplicate keys refused):

```json
{"version":1,"report":"daily","fromDay":"2026-10-01","toDay":"2026-10-22","allowedHostIds":["source-a"],"source":"session-deltas","limit":1000}
```

`report` is `daily` or `responses`. UTC dates are required, inclusive, ordered and limited to a 3660-day span. `allowedHostIds` is mandatory, distinct, at most 64 safe host labels; an empty list produces no records. `hostId` and `project` optionally narrow scope. `source` is required only for daily reports (`session-deltas` or `account-daily`). Account-daily queries refuse a project filter because those observations do not establish project attribution. `limit` defaults to 100, at most 1000 output groups. The HTTP endpoint constructs the host allowlist from current authorized active source hosts; it never accepts a caller allowlist. Query filtering must not conceal conflicting revisions or duplicate response identities by applying the date/project filter before identity reconciliation.

All successful reports have `version:1`, `engine:"duckdb"`, `engineVersion`, `receiverId`, `report`, `generatedAt` (UTC ISO timestamp), `coverage`, and `rows`. Coverage keys are `completeHistory:false`, `source:"verified-archive-projection"`, `aggregation:"known-subtotals"`, `headReconstruction:"unavailable"`, `projectedSegments`, `pendingSegments`, `projectedItems`, `archiveItems`, `lastProjectedAt` (ISO or null), `matchedRows`, `returnedRows`, `truncated`, `conflictRows`, and `excludedRows`. Counts are nonnegative safe integers. Archive/projection counts include retained V3 metadata; report row and exclusion counts concern only the requested usage family. Metadata describes the archive/projection, not completeness of provider activity. `lastProjectedAt` is a projection timestamp, not source freshness or proof that all archived data is projected. Token strings are sums of known qualified values, not complete totals where the corresponding `known` count is below the contributing row count.

Daily rows have `day`, `hostId`, `project` (nullable), `accountIdentity` (nullable), `source`, `records`, `values`, and `known`. `values` contains `input`, `cached`, `uncached`, `output`, `total`; each is an exact nonnegative decimal integer string or null. `known` has the same keys with counts of rows contributing a qualified value. Unknown is not zero. Session deltas and account totals are separate reports, and accounts remain separate per host/account identity. Resolve qualified source revisions per full logical row identity before summing. Exclude ambiguous equal-causal-time conflicting values and report their count. Source-only corrections cannot reconstruct the exact hot-cache custody head because that flag is absent from the cold format; these are archived source reports, not hot-head reconstruction.

Response rows have `hostId`, `project` (nullable), `responseCount`, `duplicateRows`, `conflictRows`, `identityMissingRows`, `excludedRows`, `totals`, `known`, `ratios`, `ratioCoverage`, and `percentiles`. `totals` has `input`, `cached`, `cacheWrite`, `output`, `reasoning`, `total` as exact nonnegative integer strings or null; `known` has corresponding contributor counts. Ratios are `cacheHit`, `reasoningShare`, `newInputFraction`, each a finite fraction [0,1] or null, calculated from comparable pairs using ratio of sums. `ratioCoverage` contains those same three keys, each with `numerator` and `denominator` (exact integer strings or null), `comparableRows`, and `excludedRows`. Percentiles are `totalP50`, `totalP95`, `outputP50`, `outputP95`, each a finite nonnegative number within the safe integer bound or null. Only independently identified candidate native response readings contribute; cumulative thread/turn totals, fork/execution/unknown classes, missing response identity and conflicting native-response readings are excluded. Repeated identical native responses are counted once per host/session/native identity, never collapsed across hosts. Context provider/model do not establish producing provider/model. No tokens-to-cost/quota or observed-time-to-generation-speed inference.

## Application boundary

`GET /api/analytics/history` is on demand, requires authenticated unrestricted administrator authority at the authoritative hub, and revalidates authority/source scope before delivery. Unsupported or unconfigured engines report unavailable. Restricted viewers and unauthenticated local preview cannot receive archive data. Gateways use their existing authenticated upstream and preserve authoritative denial. Host/project/date/report/limit parameters are allowlisted; duplicate and unknown arguments fail closed. No polling, browser rendering or live ingestion work is added by enabling the route.

The hub's private `historicalAnalytics` configuration uses a pinned dedicated SSH forced-command transport to the receiver query process; it does not carry database passwords. Its fields are `version:1`, `engine:"duckdb"`, `expectedReceiverId`, `ssh:{executable,host,port,user,identityFile,knownHostsFile}`, optional `timeoutMs` (default 20000), and optional `minIntervalMs` (default 1000). The fixed remote marker is `analytics-query`; the remote forced command must allow only `archive-analytics.py --config … --query`. An independent maintenance invocation performs `--sync`; query authority cannot invoke projection or arbitrary SQL. Transport has one in-flight request, timeout and byte bounds, disabled forwarding/agent/multiplexing, exact receiver identity checks, and bounded rate admission. Source/engine failures cannot change collection or preservation.

## Qualification boundary

Synthetic actual-engine tests and measured local workloads qualify the implementation on the tested host only. Production receiver deployment, local filesystem checks, least-privilege forced-key provisioning, actual archive catch-up, target memory/CPU measurement and independent readback are activation requirements. The optional engine is disabled until explicitly configured. A failed query or projection preserves archive bytes and pending work. Operators must retain existing archive backups and use a fresh local projection directory for a rebuild, keeping the old projection until the new one has been independently checked.

## Operator setup and recovery

1. On the archive/analytics host, verify the receiver identity, existing immutable archive/catalog paths and backup coverage. Keep the application, private configurations and engine directory controlled by the service account/root. This integration reads the existing receiver configuration and catalog locally; it does not mount active databases or download private archives to a third-party service.
2. Install the optional runtime in a dedicated local virtual environment using `python3 -m venv /opt/codexcontrol/analytics-runtime`, then `/opt/codexcontrol/analytics-runtime/bin/python -m pip install --only-binary=:all: -r /opt/codexcontrol/scripts/analytics-requirements.txt`. Review downloaded package provenance and target architecture. The qualified pin is 1.5.6; this is not a promise that every later DuckDB release is compatible.
3. Create a mode-0600 engine configuration owned by the receiver service account. For example: `{"version":1,"receiverConfig":"/etc/codexcontrol/receiver.json","databaseDirectory":"/var/lib/codexcontrol-analytics","memoryLimitMb":256,"threads":2,"queryTimeoutSeconds":15}`. These are placeholder paths, not an installed destination. Never point the projection directory at the archive or receiver catalog directory. Initialize with `archive-analytics.py --config /etc/codexcontrol/analytics.json --sync --limit 32`, then inspect `--status`. Repeat bounded sync runs until pending segments reach zero; new live segments can add further backlog.
4. Run fixed queries directly over stdin and compare known source fixtures/archived records. Example request: `{"version":1,"report":"responses","fromDay":"2026-10-01","toDay":"2026-10-22","allowedHostIds":["source-a"],"limit":100}`. Use `--query` with the same private config. Dates refer to report day or source-observation time (receipt time only where source time is absent), not projection time.
5. Provision a separate least-privilege SSH key whose authorized-key entry forces the root-controlled `deploy/analytics-query-command.sh`. That wrapper accepts only the exact `analytics-query` marker and runs the fixed query mode. Keep the existing archive sender key and forced command unchanged. Pin the independently verified host key in a separate known-hosts file; keep both the query identity file and pin file private and locally controlled. This step creates no password or SQL endpoint. This repository does not generate, display or install credentials for the operator.
6. Add the private `historicalAnalytics` object to the authoritative hub's existing configuration, with absolute paths to the installed SSH executable, query identity and pinned known-hosts file. Bind `expectedReceiverId` to the verified receiver. Restart only through the existing reviewed application deployment procedure. A gateway uses its existing authenticated upstream; do not configure a second engine/credential on the gateway. Validate unauthorized/restricted access and source revocation before accepting the deployment.
7. Review the supplied `analytics-sync.service` and timer on the archive/analytics host. They are disabled examples. Account, paths, schedule and hard resource caps need target validation before enabling them. DuckDB's memory setting is not a total process-memory guarantee; use an OS/service memory bound and measure peak RSS. Query/sync contention returns unavailable and retries on a later invocation; it does not bypass the file lock or start another writer. A bounded scheduled run may stop with remaining backlog. Observe that backlog rather than increasing concurrency blindly.

Use the authenticated CLI after activation:

```powershell
'{"query":"history-analytics","arguments":{"report":"daily","source":"session-deltas","fromDay":"2026-10-01","toDay":"2026-10-22","limit":100}}' | node .\scripts\query-codexcontrol.mjs 'C:\CodexControlPrivate\query.json'
```

The STDIO MCP equivalent is `codexcontrol_history_analytics` with the same arguments. A returned `values`/`totals` string is an exact integer subtotal; parse as an integer type capable of retaining its precision. `known` counts expose missing counters, `ratioCoverage` exposes comparable numerator/denominator populations, and `coverage.truncated` exposes output-group truncation. Do not add rows from session-delta and account-daily reports or sum copied cross-host account activity as if it were unique account usage. No gap filling or provider billing inference is performed.

To disable the integration, remove the private hub `historicalAnalytics` setting using the normal configuration/deployment procedure and stop only its optional sync timer. Preserve the analytical database for investigation and leave the archive sender and cold files running. To rebuild, stop optional sync/query operations, choose a fresh private local `databaseDirectory`, import the verified segments, compare report results and record/provenance counts, then activate that projection. Do not delete or rewrite archive data, reset receiver progress, or replace the live hub database as part of analytics recovery.

An interrupted segment transaction rolls back and can be retried in the same projection. Interruption during the initial database creation, before the schema and receiver identity commit, can instead leave an unlabeled database. Existing files with an unknown schema or receiver identity are deliberately refused without modification. Preserve that file and initialize a fresh local projection directory; do not adopt it or bypass the identity check.

## Canonical integration, 23 October 2026

The feature was reconciled with the subsequent 1.2.0 source while preserving its interface assets, live capture, verified archive receiver and GitHub runtime. The release allowlist retains both sets of files. Independent local checks exercised the actual pinned engine, authenticated HTTP, CLI/MCP, existing response compression and runtime configuration. This integration does not enable a receiver, scheduled projection or production query transport.

The independent review also reproduced and corrected a subprocess admission bug: an SSH termination error could release its physical request slot before the child exited. A child with an assigned PID now retains that slot until its close event, including failed kill escalation; a spawn failure with no owned PID still returns a bounded error. Regression fixtures use a real owned local child with the termination-error seam injected, plus an actual failed spawn. These are lifecycle checks, not deployed SSH or target-platform qualification.

## Local qualification, 22 October 2026

The final combined run on the frozen GitHub integration base `c8326e7e1470e78ffe6005f8f2240cd840b43c74` selected 23 test files and completed 305 checks: 301 passed, none failed, and four POSIX-only cases were skipped on Windows. Actual DuckDB 1.5.6 tests were enabled through `CODEX_ANALYTICS_PYTHON`, including all 13 engine tests and the receiver-to-engine-to-authenticated-HTTP integration test. The run covered analytics API/transport/CLI/MCP, existing preservation/authorization, and both GitHub integration test files after reconciliation. Windows owner-private key/pin ACL refusal was exercised. The forced-command shell wrapper passed syntax validation; deployed SSH and Linux service behavior remain untested.

Independent review reproduced and verified corrections for database mutation before identity refusal, per-segment catalog query overhead, JSON-key-order false conflicts, conflict-only response validation, accepted year-zero records, and unknown account observation times. The new V3 archive family exposed an importer stall, which was reproduced and corrected against a copied snapshot of the actual receiver. A mixed V1/V2/V3 segment retained all three exact records, replay imported zero additional items, GitHub counters stayed null, and both usage reports retained only their respective contributor. Independent review verified that evidence and preservation of GitHub runtime hooks during the server merge. Tests also cover real process termination during an uncommitted segment, exact retry, malformed requests, source/viewer revocation, byte bounds, SQL interruption, null counters, ratios and integer sums beyond JavaScript's safe range. Archive and catalog fingerprints remained unchanged.

A separate synthetic workload retained 20,000 records in 20 verified segments: 16,000 distinct native responses, 1,600 replay observations, 2,000 daily row identities and 400 later daily revisions. Raw input was 28,725,474 bytes and compressed input 2,913,766 bytes. ## Primary technical references

- [DuckDB 1.5 concurrency](https://duckdb.org/docs/1.5/connect/concurrency): the native database uses process/file locking; this implementation uses one optional writer and bounded read-only invocations.
- [DuckDB security controls](https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview): fixed SQL, disabled external access/extension installation and controlled files reduce exposure. These controls supplement the trusted service-account boundary; they do not turn an arbitrary database file or SQL string into safe untrusted input.
- [DuckDB configuration](https://duckdb.org/docs/stable/configuration/overview): memory, thread and temporary-storage settings are explicit and tested against the pinned runtime.
